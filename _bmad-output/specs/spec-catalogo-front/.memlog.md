- (direction) fontes: README.md, docs/referencia-api/ (contrato da API) e descrição colada pelo usuário; modo express; slug catalogo-front
- (decision) Why: mandato do TCC; o front valida o Golden Path frontend de ponta a ponta; escopo mínimo porque o foco é a plataforma
- (capability) CAP-1 listar produtos com busca por nome, filtros (status, faixa de preço), ordenação e paginação, seguindo produto.md; inativos visualmente distintos
- (capability) CAP-2 cadastrar produto (POST /produtos); 201 mostra o produto criado
- (capability) CAP-3 ver detalhe de um produto (GET /produtos/{id}); link direto funciona; 404 vira mensagem de não encontrado
- (capability) CAP-4 editar produto ativo ou desativado (PUT, substituição total), formulário pré-preenchido
- (capability) CAP-5 desativar e reativar (PATCH /produtos/{id}/status); a mudança aparece na listagem e no detalhe
- (capability) CAP-6 URL da API definida em tempo de execução por variável de ambiente do contêiner (ex.: config.json gerado no start); mesma imagem para qualquer ambiente
- (capability) CAP-7 /healthz no servidor estático responde 200 sem depender da API
- (capability) CAP-8 erros da API exibidos com clareza: erros de validação junto ao campo, ProblemDetails title/detail nos demais, falha de rede com mensagem própria
- (constraint) consome a catalogo-api exatamente pelo contrato de docs/referencia-api (rotas, enums pelo nome, ProblemDetails, OpenAPI /openapi/v1.json); o front não redefine nada
- (constraint) URL da API nunca no build nem no repositório; injetada no start do contêiner
- (constraint) o navegador chama a API direto em outro host (CORS); a API é a dona do CORS (AD-8)
- (constraint) Golden Path do front obrigatório: linux/arm64, servidor estático não-root (ex.: nginx-unprivileged) com /healthz, ci.yml → frontend-service.yml, manifestos e segredos fora do repo; detalhado em golden-path.md
- (constraint) sem OpenTelemetry no navegador; sem autenticação
- (constraint) testes unitários rodam e passam com npm test -- --watch=false --browsers=ChromeHeadless (comando da esteira); o runner precisa aceitar essas flags
- (constraint) UX: layout simples e responsivo; acessibilidade básica: rótulo em todo campo, operação completa por teclado, contraste adequado
- (decision) non-goals: login, i18n, trace no navegador, PWA/offline; mais remoção de produto (a API não tem) e alterar a infraestrutura comum (template de esteira, golden-path/base)
- (decision) success signal: o front executa todas as operações da API pelo cluster, publicado pela esteira, sem alterar a infraestrutura comum
- (decision) companions: golden-path.md (spec-authored, obrigações do front); SPEC.md, produto.md e ARCHITECTURE-SPINE.md da API adotados de docs/referencia-api; README em sources
- (assumption) interface só em pt-BR (decorre do non-goal i18n)
- (assumption) contraste mínimo WCAG 2.1 AA (4.5:1 em texto normal); o usuário não deu número
- (assumption) servidor estático na porta 8080 (padrão do nginx-unprivileged), SPA servida na raiz do próprio host, fallback para index.html nas rotas da SPA
